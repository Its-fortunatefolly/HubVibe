## How an agent uses this

1. **Discover**: `GET https://hubvibe-io.com/discover?q=<intent>` or `POST https://hubvibe-io.com/discover/semantic` with `{"query": "<intent>", "limit": 3}`. The answer is ranked candidates (canonical id, route, price, schemas, contract URL) with `method` saying how they were ranked (`sparse_bm25`, `dense_minilm`, `hybrid_bm25_minilm_rrf`); `status` is `candidates`, `ambiguous` (ask the buyer which job they mean) or `no_match`. `GET https://hubvibe-io.com/discover/health` says which methods are live; `GET https://hubvibe-io.com/discover/catalog-version` changes when anything here changes. Discovery never runs a job or reads a payment.
2. **Verify**: `GET https://hubvibe-io.com/contracts/<id>` is the purchase contract (schemas, price, pay-to, hash). `POST https://hubvibe-io.com/contracts/<id>/verify` checks your terms and body first, free.
3. **Buy**: POST the route; the unauthenticated answer is HTTP 402 with the payment challenge (x402 on Base or Solana, MPP, or a prepaid key). Pay through your own wallet or the buyer router (`wcag-audit-engine/integrations/hubvibe_router.py`); send `X-HubVibe-Contract: <contract_hash>` so a changed contract refuses the payment.
4. **Receive**: the 200 carries the result and a `receipt_id`; `GET /work/receipts/<id>` is the receipt. A job that produced no result is never charged.

## Routing contract

- One inventory: discovery, `/work`, `/contracts`, OpenAPI, the MCP tool list, the A2A card and these files are generated from the same catalog; an id in one is the same id everywhere.
- Candidates, not decisions: discovery proposes; the agent (or its buyer router) verifies the contract, checks its budget and pays. Nothing is executed because it matched.
- `ambiguous` is an answer: when the top candidates are too close to tell apart, the node says so instead of forcing one. `no_match` means no sold capability fits the words, not that the job is impossible.
- Only what is sold now is indexed; a worker without its provider is neither listed nor priced.

## What this does not claim

- Publication of these files does not place HubVibe in any third-party registry or vector store; each registry ingests what it crawls or is given through its own process.
- `identity.check` establishes mailbox, DNS and wallet ownership and public-record matches. It is not government-ID or biometric identity verification and is never described as KYC.
- `market.signal` and `market.forecast` are statistical descriptions of history with stated uncertainty, not calibrated predictions or advice.
- A ranking score is relevance, not a probability that the tool can do the job; the buyer verifies the contract and input schema before paying. `ambiguous` means the node will not choose for you.
- Dense retrieval uses a local pinned model (sentence-transformers/all-MiniLM-L6-v2, Apache-2.0, revision `1110a243fdf4706b3f48f1d95db1a4f5529b4d41`); a node whose model is not loaded says so on `/discover/health` and labels its answers `sparse_bm25`.
